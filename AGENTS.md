# AGENTS.md — Dублёр / Film Backup Pro

Этот файл содержит обязательные инструкции для AI-агентов, работающих с проектом.
Правила распространяются на весь репозиторий, если более вложенный `AGENTS.md` явно
не задаёт дополнительные ограничения для своей директории.

## 1. Проект

- Название продукта: **Dублёр**.
- Кодовое название: **Film Backup Pro**.
- Назначение: безопасное резервное копирование фото-, видео- и аудиоматериалов
  с внешних носителей на выбранный диск.
- Целевая платформа: **только macOS**.
- Язык: Python.
- Поддерживаемый Python для разработки и сборки: **3.11 или 3.12**.
- UI: **PySide6 / Qt Widgets**, стиль Fusion.
- Точка входа: `app.py`.
- Composition root: `composition.py`.
- Основной источник версии: `ui_new/main_window_new.py`, `AppNew.APP_VERSION`.
- Журнал проекта: `PROJECT_LOG.md`.

Всегда отвечай пользователю на русском языке, если он явно не попросил другой язык.

## 2. Главный приоритет

Надёжность пользовательских данных важнее скорости разработки и косметических
улучшений.

- Не ослабляй проверку целостности без прямого запроса пользователя.
- Не удаляй и не изменяй исходные пользовательские файлы.
- Не тестируй потенциально разрушающие сценарии на реальных единственных копиях данных.
- Для тестов копирования, конфликтов, удаления и извлечения используй временные каталоги
  и тестовые носители.
- Не сообщай об успешном копировании до завершения выбранной проверки.
- При ошибке, отмене или частичном результате сохраняй диагностический контекст и
  корректно освобождай ресурсы.
- Перед изменением логики извлечения томов проверяй, что команда применяется только к
  корню `/Volumes/<имя тома>`, а не к произвольному или вложенному пути.

## 3. Архитектурные границы

Соблюдай SOLID и KISS. Предпочитай минимальное решение с одной ответственностью.

### Основные слои

- `app.py` — запуск Qt-приложения и ранняя инициализация; без бизнес-логики.
- `composition.py` — создание и связывание общих зависимостей.
- `ui_new/`, `ui/`, `widgets/`, `ui_forms/` — UI, Controller и ViewModel.
- `backup_process_controller.py`, `backup_launcher.py` — проверка входных данных,
  создание компонентов запуска и старт фоновой операции.
- `engine.py`, `engine_modules/` — вход в движок, сканирование, категории и структура проекта.
- `backup_components/` — копирование, проверка, дедупликация, хеши, прогресс и оркестрация.
- `repositories/` — доступ к файловой системе.
- `interfaces.py` — Protocol-контракты.
- `config.py`, `paths.py`, `logger.py` — инфраструктура.

### Обязательные правила

- Новые общие зависимости подключай через `composition.py` и передавай явно.
- Для файловой системы используй `IFileSystemInterface` / `FileSystemRepository`,
  если слой уже работает через эту абстракцию.
- Не добавляй новые обращения к глобальному `get_current_context()`:
  это legacy-механизм переходного периода.
- UI не должен выполнять копирование, хеширование или длительное сканирование.
- Фоновый код не должен напрямую изменять Qt-виджеты.
- Для связи worker-потоков с UI используй Qt signals/slots.
- Не создавай второй источник истины для состояния, категорий, путей или статистики.
- Перед добавлением helper-функции ищи существующую реализацию через `rg`.
- Не дублируй стили и числовые UI-константы; используй `themes.py` и
  `ui/ui_constants.py`.
- Сохраняй публичные контракты при рефакторинге. Совместимые адаптеры допустимы только
  как временный, явно отмеченный слой.

## 4. UI и потоки

- Используй только PySide6/Qt Widgets; не добавляй Tkinter и другие UI-фреймворки.
- Сохраняй `QApplication.setStyle("Fusion")`.
- Длительные операции выполняй вне главного UI-потока.
- Повторный запуск таймера или анимации должен предварительно останавливать и
  синхронизировать предыдущее состояние.
- Для размеров, отступов и длительности анимаций используй существующие константы.
- Для стандартных плавных анимаций предпочитай `QPropertyAnimation` и
  `QEasingCurve.InOutQuad`.
- После UI-изменений проверяй не только внешний вид, но и состояние, сигналы,
  быстрые повторные действия, закрытие, отмену и повторный запуск.
- Не обращайся к private-полям другого компонента без необходимости. Если это нужно
  нескольким потребителям, добавь узкий публичный метод.

## 5. Файловые операции и конфигурация

- Важные JSON, настройки и хранилища записывай атомарно: временный файл, flush/close,
  затем replace.
- Валидируй источник и назначение перед файловой операцией.
- Канонизацию путей не реализуй повторно; используй общую реализацию проекта.
- Не хардкодь абсолютные machine-specific пути.
- Runtime-пути приложения получай через `paths.py`.
- Fallback должен быть детерминированным, ограниченным и покрытым тестом.
- При обработке конфликтов не меняй политику пользователя скрытым образом.
- Новые системные команды запускай списком аргументов без `shell=True`.

## 6. Код и ошибки

- Пиши чистый, поддерживаемый и минимально сложный код.
- Добавляй type hints в новые и изменённые публичные функции.
- Выбирай имена, описывающие намерение.
- Декомпозируй большие методы; ориентир — одна ответственность, а не формальное число строк.
- Удаляй неиспользуемые импорты, временный debug-код и мёртвые ветки в области изменения.
- Не выполняй несвязанный рефакторинг без запроса.
- Не используй `print()` в новом runtime-коде. Для приложения используй:

  ```python
  logger = logging.getLogger(__name__)
  ```

- CLI-скрипты могут использовать stdout как пользовательский интерфейс.
- Не используй `bare except:`.
- Перехватывай конкретные исключения.
- Не глотай исключения без объяснения. Если `pass` безопасен и необходим, добавь
  короткий комментарий.
- Логируй этап, путь и причину ошибки, но не записывай токены и другие секреты.

## 7. Окружение и зависимости

- Всегда используй виртуальное окружение проекта.
- Не устанавливай зависимости в системный Python.
- Основные команды:

  ```bash
  .venv/bin/python app.py
  .venv/bin/python -m pytest ...
  .venv/bin/python -m pip install -r requirements.txt
  ```

- Для production/universal2-сборки используй `.venv_universal2` и Python 3.11/3.12
  с python.org.
- Не добавляй зависимость, если задача решается стандартной библиотекой или уже
  установленным пакетом без ухудшения читаемости и надёжности.
- При добавлении или удалении зависимости синхронизируй:
  `requirements.txt`, spec-файлы, build-скрипты и документацию.
- Не удаляй транзитивные зависимости вручную, если они нужны прямому пакету.

## 8. Проверка изменений

Сначала запускай узкие тесты затронутого поведения, затем подходящие полные проверки.

### Синтаксис изменённых модулей

Чтобы не писать `__pycache__` в проект:

```bash
PYTHONPYCACHEPREFIX=/tmp/dubler-pycache \
  .venv/bin/python -m py_compile <изменённые файлы>
```

### Полный набор без GUI

```bash
PYTHONDONTWRITEBYTECODE=1 DUBLER_AGENT_LOG=0 \
  .venv/bin/python -m pytest tests \
  --ignore=tests/test_ui_new_components.py -q
```

### GUI-тесты

```bash
PYTHONDONTWRITEBYTECODE=1 DUBLER_AGENT_LOG=0 QT_QPA_PLATFORM=offscreen \
  .venv/bin/python -m pytest tests/test_ui_new_components.py -q
```

Текущее локальное `.venv` может использовать Python 3.14. При нём известен `SIGSEGV`
на этапе выгрузки Qt после того, как GUI-тесты дошли до 100%. Не выдавай этот teardown
за падение конкретного теста, но обязательно сообщай о нём. Для окончательной
валидации используй поддерживаемый Python 3.12.

### Smoke и архитектурные контракты

```bash
DUBLER_AGENT_LOG=0 .venv/bin/python scripts/smoke_all.py
```

Не удаляй скрипты из `scripts/`: они являются safety net рефакторинга.

### Минимальная матрица

- Изменение UI: релевантные unit-тесты + `test_ui_new_components.py`.
- Копирование/проверка/дедупликация: профильные тесты + полный набор без GUI +
  `smoke_all.py`.
- Пути/конфигурация/DI: профильные тесты backward compatibility + контракты.
- Сборка: только по явному запросу пользователя и после тестов.

В финальном отчёте указывай точные результаты: сколько тестов прошло, что было
пропущено, и была ли проблема теста или окружения.

## 9. Версия и журнал изменений

- Источник версии: `ui_new/main_window_new.py`, `APP_VERSION`.
- Для локального исправления или внутреннего рефакторинга: `+0.0.1`.
- Для заметной новой функции или изменения основного пользовательского сценария:
  `+0.1.0`.
- `+1.0.0` выполняй только по прямому решению пользователя.
- После заметного изменения кода или поведения:
  1. обнови `APP_VERSION`;
  2. синхронизируй версию в `README.md`;
  3. добавь запись в начало `PROJECT_LOG.md`;
  4. обнови явное упоминание текущей версии в `BUILD_INSTRUCTIONS.md`, если оно есть.
- Только документация, тесты или сам `AGENTS.md` не требуют повышения версии, если
  пользователь не попросил иначе.
- Не переписывай исторические записи `PROJECT_LOG.md`; добавляй новую запись.
- Для обычного patch bump следуй локальному skill `bump-version`, если он доступен.

## 10. Сборка и релиз

- Не запускай полную сборку или создание DMG без явного запроса пользователя.
- Для релизной сборки используй локальный skill `build-dmg`, если он доступен.
- Каноническая команда:

  ```bash
  ./build.sh
  ```

- Сборка создаёт или заменяет содержимое `build/` и `dist/`; перед запуском проверь
  точный scope и получи необходимые разрешения.
- Не применяй широкие destructive-команды к корню проекта или пользовательским данным.
- После сборки проверь существование `.app`, DMG, архитектуру бинарника и результат
  codesign согласно `BUILD_INSTRUCTIONS.md`.

## 13. Рабочий процесс агента

1. Прочитай запрос и затронутые модули.
2. Если смысл изменения materially неоднозначен или может повредить данные, уточни.
3. Проверь существующую реализацию и тесты через `rg`.
4. Сформулируй минимальный scope.
5. Внеси изменение, сохраняя архитектурные границы.
6. Добавь или обнови тесты поведения.
7. Выполни подходящие проверки из раздела 8.
8. Удали временную диагностику и неиспользуемый код.
9. При необходимости обнови версию и `PROJECT_LOG.md`.
10. Сообщи пользователю результат, тесты, ограничения и оставшиеся риски.

## 14. Definition of Done

Задача считается завершённой, когда:

- требуемое поведение реализовано;
- безопасность исходных данных не ухудшена;
- нет нового дублирования и ненужной связанности;
- изменённые публичные методы имеют понятные контракты;
- релевантные тесты добавлены и пройдены;
- smoke/contract-проверки пройдены, если затронут движок или архитектура;
- временные логи, debug-код и неиспользуемые импорты удалены;
- версия и журнал синхронизированы, если изменение этого требует;
- итоговый отчёт отделяет дефекты кода от проблем окружения.
