# Распознавание дубликатов при добавлении файлов, уже имеющихся в проекте

## Текущее состояние

В проекте **нет дедупликации по содержимому**. В `backup_components/deduplication_manager.py` указано: «Индекс назначения по размеру и A/B/C дедупликация удалены; конфликты решаются диалогом „Файл уже существует“».

Остаётся только **конфликт по пути** (`_resolve_destination_conflict`): если в назначении уже есть файл **по тому же пути** — показывается диалог (Заменить / Пропустить / Оставить оба). Если тот же контент лежит **в другом месте** проекта, он не считается дубликатом и файл копируется повторно.

В тесте `test_deduplication_full_mode.py` это зафиксировано: «Дубликаты по содержимому в другом пути **больше не пропускаются** автоматически».

**Итог:** при добавлении файлов/папок, которые уже есть в проекте по содержимому (но по другому пути), система распознавания дубликатов не срабатывает. Нужно снова ввести проверку «такой же контент уже в назначении».

---

## 5 вариантов решения

### 1. Дедупликация по содержимому на этапе копирования (классический вариант)

**Идея:** Перед копированием каждого файла (или в начале этапа копирования) строить индекс файлов в назначении: по размеру → при совпадении по sample_signature → при совпадении по MD5. Для каждого файла из источника перед копированием вызывать проверку (аналог `_try_skip_as_duplicate_full_mode`): если в назначении найден файл с тем же содержимым — не копировать, а считать «пропуск как дубликат» и обновлять статистику.

**Где менять:** `CopyPlanAndExecuteService` (например, в `copy_file_from_directory` / `process_single_file` перед `_resolve_destination_conflict` или перед вызовом `copy_file`). Индекс назначения можно строить один раз в начале `copy_all_files` (обход `project_root`) или подгружать лениво.

**Плюсы:** Один понятный момент применения логики — этап копирования; сканирование и добавление источников не трогаем.  
**Минусы:** Нужно заново реализовать построение индекса назначения и проверку дубликата (как в старых планах cheap-first дедупликации).

---

### 2. Фильтрация дубликатов по содержимому на этапе сканирования

**Идея:** В список «что копировать» вообще не попадают файлы, которые уже есть в проекте по содержимому. После (или внутри) `scan_sources_unified` построить индекс существующих файлов в `project_root` (размер, при необходимости sample_signature/MD5 для кандидатов). При формировании `files_list` для каждого файла-источника проверять: есть ли в проекте файл с тем же содержимым; если да — не добавлять в список.

**Где менять:** `engine_modules/scanning.py` (`scan_sources_unified`) или отдельная функция «пост-фильтр» по уже собранному `ScanResult` и по индексу назначения.

**Плюсы:** Дубликаты не доходят до копирования — меньше работы и проще логика копирования.  
**Минусы:** Нужно один раз просканировать назначение и считать хеши; сканирование усложняется или появляется отдельный проход.

---

### 3. Отдельный этап «Дедупликация» между сканированием и копированием

**Идея:** После того как список файлов получен (`scan_sources_unified` / `all_files_to_copy`), но до `copy_all_files`, выполнять этап «фильтр дубликатов»: построить индекс назначения (размер → sample_signature → MD5), пройти по `all_files_to_copy` и выкинуть те записи, для которых в назначении уже есть файл с тем же содержимым; пересчитать `total_bytes`, счётчики и т.д.

**Где менять:** Цепочка этапов в оркестраторе (например, в `CopyingStage` или отдельный шаг перед ним), плюс сервис/функция, которая принимает список файлов и индекс назначения и возвращает отфильтрованный список.

**Плюсы:** Чёткое разделение: сканирование → дедупликация → копирование; логику дедупликации удобно тестировать отдельно.  
**Минусы:** Дополнительный проход по назначению и по списку файлов.

---

### 4. Проверка при добавлении источника или перед стартом бэкапа

**Идея:** Не только «этот путь уже в списке источников», но и «часть файлов из этого источника уже есть в проекте по содержимому». При добавлении источника (или по кнопке «Старт») строить индекс проекта (хотя бы по размеру, при совпадении — sample/MD5) и сверять файлы из нового источника с ним. Показывать уведомление: «N файлов уже есть в проекте и будут пропущены» и/или опцию в настройках/диалоге «Пропускать дубликаты по содержимому».

**Где менять:** UI (например, `MainWindowController.add_sources` или место запуска бэкапа), плюс отдельный модуль/функция проверки «источник vs проект» с использованием того же типа индекса, что и для дедупликации при копировании.

**Плюсы:** Пользователь сразу видит, что часть файлов будет пропущена как дубликаты.  
**Минусы:** Либо тяжёлая операция при добавлении источника, либо сдвиг на момент «Старт»; в любом случае нужен индекс назначения и договорённость, что «пропуск дубликатов» потом действительно выполняется на этапе копирования (см. п. 1 или 3).

---

### 5. Постоянный индекс содержимого в проекте (инкрементальная дедупликация)

**Идея:** В самом проекте (например, в `.film_backup` или рядом с MD-логом) хранить индекс уже находящихся в проекте файлов: путь, размер, sample_signature, MD5. При следующем запуске (и при добавлении «файлов, которые уже есть в проекте») загружать этот индекс и при копировании проверять новые файлы по нему: совпадение по содержимому → пропуск. Индекс обновлять после каждого успешного копирования или в конце этапа.

**Где менять:** Новый компонент «индекс проекта» (чтение/запись в проект), интеграция в этап копирования (как в п. 1) или в этап дедупликации (как в п. 3), при необходимости — в `HashStorage` или отдельное хранилище.

**Плюсы:** Не нужно каждый раз заново сканировать всё дерево назначения; удобно при многократных добавлениях одних и тех же файлов в уже существующий проект.  
**Минусы:** Нужно хранить и поддерживать индекс в проекте и учитывать его при любых изменениях файлов в проекте извне.

---

## Резюме

Сейчас распознавание дубликатов «не срабатывает» именно потому, что проверка по **содержимому** в назначении удалена; остаётся только конфликт по **пути**. Чтобы это исправить, нужно снова ввести сравнение по содержимому (размер → sample_signature → MD5) и один из вариантов: проверка при копировании (1), фильтрация при сканировании (2), отдельный этап дедупликации (3), предупреждение при добавлении/старте (4) или постоянный индекс в проекте (5). Наиболее прямой способ — вариант 1 (дедупликация в момент копирования с индексом назначения); варианты 2 и 3 дают ту же логику с другим местом применения; 4 и 5 улучшают UX и инкрементальные сценарии.
